# darwin-bot 架构改进建议

> 目标：把当前混在一起的代码重构为**可扩展、可维护、便于并行 PR** 的项目。本文只分析问题与给方向，不改代码。

---

## 一、当前现状盘点

### 1.1 仓库由三个互相缠绕的包组成

| 包 | 入口 | 职责 | 打包配置 |
|---|---|---|---|
| `robopal/` | `setup.py` | 机械臂仿真环境（MujocoEnv / robots / controllers） | `setup.py` 只打 `robopal*` |
| `ragbot/` | `pyproject.toml` | RAG 经验记忆层 | `pyproject.toml` 只打 `ragbot*` |
| `darwin/` | **无** | 智能体 + 规划器 + IPC + skills + 进化系统 | **没有任何打包配置** |

`darwin` 是项目核心，却既没有 `setup.py` 也没有 `pyproject.toml` 项；只能靠 `PYTHONPATH` 凑齐 `from darwin.xxx import yyy`。三个包没有清晰的依赖方向：`darwin` 同时 `import robopal` 和 `import ragbot`，`robopal/envs/base.py` 又会通过 forged skill 反向调用 `darwin` 的回调（`env._darwin_post_step`），形成隐式双向耦合。

### 1.2 体量 Top 10 文件

| 文件 | 行数 | 性质 |
|---|---|---|
| `scripts/make_jarvis_video.py` | 1149 | 脚本，超出脚本应有体量 |
| `darwin/agents/runner_dynamic.py` | 996 | God class |
| `darwin/skills/primitives/__init__.py` | 677 | 包入口塞了 11 个 Skill 实现 |
| `darwin/skills/primitives/control.py` | 598 | 控制原语 |
| `darwin/agents/chain_registry.py` | 575 | 注册表（设计本身合理） |
| `darwin/envs/libero_adapter.py` | 474 | 适配器 |
| `robopal/controllers/planners/rrt.py` | 463 | RRT 规划器 |
| `robopal/envs/base.py` | 432 | 环境基类 |
| `ragbot/memory/rag.py` | 423 | RAG 记忆（与 darwin/memory/rag.py 几乎重复） |
| `darwin/agents/methods.py` | 407 | Method 基类 + 内置方法 |

### 1.4 设计模式使用现状

| 已用 | 在哪 | 是否规范 |
|---|---|---|
| 策略模式 | `Method` / `DeclarativeMethod` / `ForgedSkillMethod` | 规范 |
| 注册表 | `ChainRegistry` (list+map 双层) | 规范 |
| 模板方法 | `Method.make_steps` | 规范 |
| 工厂 | `robopal.envs.base.make` | 规范 |
| 进程单例 | `default_registry()` 全局可变 | 不规范，多任务并行时无法隔离 |
| lambda 回调事件流 | `event_cb=lambda ev: ...` | 半规范，没有统一的 EventBus |
| `if msg.type ==` 分发 | `sim_worker._serve_conn` | 反模式，应该用 dispatch table |

| 应该用但没用 | 当前现状 |
|---|---|
| 命令模式 | skill 是 `{"action":..., "params":...}` dict，不是对象；skill 执行结果散落 |
| 状态模式 | attempt / resume / stopped 状态由 `_last_cand` / `_last_method_name` / `_last_body0` 等散落字段维护 |
| 适配器 | `libero_adapter.py` 474 行过重；`_darwin_kind == "insert"` 仍是 if-else 分支 |
| 观察者 | 物理观测靠 `env._darwin_physics_obs` 这种 monkey-patch 字段 |
| 依赖注入 | `DynamicEpisodeRunner` 在构造里直接 `ManipulationAgent(...)`、`ExperienceStore()`，难替换 |

## 二、核心问题（按严重性排序）

### 🔴 P0-1：RAG 记忆层双份代码

**问题**：[ragbot/memory/rag.py](file:///home/lifd/Public/darwin-bot/ragbot/memory/rag.py)（423 行）与 [darwin/memory/rag.py](file:///home/lifd/Public/darwin-bot/darwin/memory/rag.py)（399 行）几乎是逐行复制，只在环境变量名上不同：

- `ragbot/memory/rag.py:48` 读 `RAGBOT_EMBED`
- `darwin/memory/rag.py:54` 读 `DARWIN_RAG_EMBED`

两份 `MemoryStore`、两份 `_SemanticIndex`、两份 `size_band_of`、两份 `LEGACY_JSON` 迁移逻辑、两份经验目录（`ragbot/memory/experience/` 与 `darwin/memory/experience/`）。`docs/01_rag_memory.md` 还在文档里教用户 `from ragbot import RAGMemory`，而 `darwin` 内部却用自己的副本。两套记忆无法互通、无法共享同一份经验沉淀。

**影响**：bugfix 要改两处；经验沉淀分散在两个目录；扩展第三种记忆后端要写三遍。

### 🔴 P0-2：`darwin` 没有打包配置

**问题**：根目录 [pyproject.toml](file:///home/lifd/Public/darwin-bot/pyproject.toml) 只声明 `include = ["ragbot*"]`；[setup.py](file:///home/lifd/Public/darwin-bot/setup.py) 只打 `robopal*`。`darwin` 这个最核心的包没有任何打包入口。

**影响**：
- `pip install -e .` 装不到 `darwin`，必须靠 `PYTHONPATH` 凑；
- `darwin/skills/forged/<task>/entry.py` 这类多层嵌套包没有显式 `__init__.py` 路径声明，`find_packages()` 行为不可控；
- `darwin-bot.egg-info` 与 `ragbot.egg-info` 两套 egg-info 并存，分支切换后常残留旧 metadata；
- 装到不同机器上行为不一致。

### 🔴 P0-3：`sim_worker.py` 是 God Class

**问题**：[darwin/ipc/sim_worker.py](file:///home/lifd/Public/darwin-bot/darwin/ipc/sim_worker.py) 400 行，`SimWorker` 一个类承担 9 项职责：

| 行号 | 职责 |
|---|---|
| L53-64 | 任务名解析 + env 标签判定 |
| L67-101 | runner / store / physics 装配 |
| L106-134 | 物理快照环形缓冲 + 回退点定位算法 |
| L138-162 | 是否可续跑判定 |
| L166-280 | 消息分发 + attempt/resume 处理 + 异常包装 + 结果组装 |
| L318-322 | IPC 消息发送 |
| L327-380 | 监听循环 + accept/serve 协议握手 |
| L383-396 | CLI 入口 |

类内字段 `_last_cand` / `_last_method_name` / `_last_body0` / `_last_failed_action` / `_n_resume` 在 attempt 与 resume 之间隐式传状态，是一个隐式状态机，但代码里没有把状态显式建模。

**影响**：改一个协议字段要读全文件；新增消息类型要在 `_serve_conn` 里再加 `if`；状态字段散落，调试时不知道哪个时刻哪个值有效。

### 🔴 P0-4：`DynamicEpisodeRunner` 是更大的 God Class

| L663-721 | prepare/teardown episode |

### 🟠 P1-5：`primitives/__init__.py` 是 677 行巨型 facade

**问题**：[darwin/skills/primitives/__init__.py](file:///home/lifd/Public/darwin-bot/darwin/skills/primitives/__init__.py) 是包入口，却在里面实现了 11 个 `Skill` 子类（`HomeSkill` / `MoveAboveSkill` / `DescendSkill` / `CloseGripperSkill` / `OpenGripperSkill` / `LiftSkill` / `MoveToSkill` / `MoveToXYTopSkill` / `PlaceSkill` / `PullDrawerSkill` / `ArticulateJointSkill`），加上 `_autodoc_params()` 元编程在 `globals()` 上反射注册参数 schema，最后 `from .control import *` / `from .motion import *` / `from .collision import *` / `from .ik_servo import *` 把 4 个子模块全 star-import 进来。

**影响**：
- 包入口 = 实现集 = 元编程注册器 = 4 路星式 import，四种职责揉一起；
- 单测想只 import `HomeSkill` 必须把整包（含 mplib/GraspNet 等重依赖）全加载；
- `from .control import *` 这种 star import 是循环 import 风险的高发区（注释 `# 避免循环 import` 已经在文件里出现）；
- 新增第 12 个原语要改这个 677 行文件，PR 冲突率高。

### 🟡 P2-1：完全没有 CI/CD

**问题**：仓库根目录无 `.github/workflows/`、无 `.gitlab-ci.yml`、无 `.pre-commit-config.yaml`、无 `tox.ini` / `noxfile.py` / `pytest.ini`。

**影响**：
- 13 个 `tests/test_*.py` 永远只能本地手跑；
- `scripts/test_*.py` 那批文件根本不在 pytest 默认收集路径，实际没跑过；
- 没有格式检查 / lint / 类型检查；
- "大规模并行 PR" 没有自动验证机制，merge 后果不可预测。

### 🟡 P2-2：测试覆盖严重不均

**现状**：`tests/` 下 13 个测试全部针对 `robopal`（quat / calibrate / register / controller / xml_splice / transform / wrappers / petting_paral / sb3 / rllib 等）。`darwin/`（agent / runner / chain_registry / sim_worker / methods / skills）与 `ragbot/`（RAGMemory / MemoryStore）**零单元测试**。

**影响**：重构 `darwin` 时没有回归保护；改 `chain_registry.select` 算法只能靠端到端 sim 跑一遍验证。

### 🟡 P2-3：单进程可变全局单例

**问题**：[chain_registry.py L335-357](file:///home/lifd/Public/darwin-bot/darwin/agents/chain_registry.py#L335) `default_registry()` 是进程级 `_DEFAULT` 全局变量，进程内第一次调用注册所有内置 method + 扫 `methods/*.yaml` + load_forged。`reset_default_registry()` 暴露给测试用，但生产路径不可重入。

**影响**：
- 同进程跑两个不同 task 时，第一个 task 的 `reorder_by_experience` 把方法顺序改了，第二个 task 在被污染的顺序上规划；
- 在 `sim_worker` 常驻进程里跨 attempt 状态泄漏（forged skill 不断 append，注册表越来越大）；
- 多线程 / 多 worker 并行实验不可行。

### 🟡 P2-4：`forged skill` 持久化在代码树里

**问题**：`darwin/skills/forged/<task_name>/entry.py` 共 7 个子目录（libero_goal_00/07、pickplace、pick、any、drawer_place、peg_in_hole、robust_grasp），每个是一个动态生成的成功轨迹快照。`load_forged` 在每次 `default_registry()` 时扫盘注册。`logs/snapshots/good/darwin/skills/forged/` 还有一份镜像。

**影响**：
- 这是运行时生成的数据，却放在源代码包里，会被 `pip install` 打包出去；
- 同名 skill 反复生成覆盖时 git diff 巨大；
- 没 forge 失败回滚 / 版本号机制。

## 三、推荐的目标架构

### 3.1 分层与依赖方向

```
        ┌─────────────────────────────────────────────┐
        │         scripts/  (CLI 入口层，无业务)        │
        └──────────────────┬──────────────────────────┘
                           ▼
        ┌─────────────────────────────────────────────┐
        │  darwin.app  (用例编排：run_episode / ipc)  │  ← 仅此层组合多模块
        └─────┬───────────────────────┬───────────────┘
              ▼                       ▼
   ┌──────────────────────┐   ┌──────────────────────┐
   │  darwin.agents        │   │  darwin.skills        │
   │  (planner/runner)     │   │  (Skill primitives)   │
   └─────┬──────────────────┘   └──────────┬──────────┘
         ▼                                  ▼
   ┌──────────────────────┐   ┌──────────────────────┐
   │  darwin.memory       │   │  ragbot (独立 PyPI)   │
   │  (memory/rag 薄壳)    │◄──┤  RAGMemory           │
   └──────────────────────┘   └──────────────────────┘
         ▲                                  ▲
         │             (env 适配层)          │
   ┌─────┴──────────────────────────────────┴──────┐
   │   robopal (独立 PyPI，不反向依赖 darwin)       │
   │   - MujocoEnv / robots / controllers          │
   │   - darwin 通过 DarwinEnvWrapper 注入回调       │
   └───────────────────────────────────────────────┘
```

依赖方向严格自上而下。`robopal` 永远不 `import darwin`，`darwin` 通过**显式注入的回调对象**（不是 monkey-patch 字段）让 env 反馈事件。

### 3.2 包结构建议

```
darwin-bot/
```

### 3.3 设计模式落地

| 模式 | 落地位置 | 解决什么 |
|---|---|---|
| 命令模式 | `Skill` 升级为 `Command` 对象，`execute(env, params)` 返回 `Result` 对象（不只是 dict） | skill 行为统一、可重放、可单测 |
| 策略模式 | `Method` 已有；保留 | 任务-方法解耦 |
| 注册表 | `ChainRegistry` 已有；**改成实例而非进程单例** | 多任务并行隔离 |
| 状态模式 | `SimWorker` 显式 `WorkerState` enum：`IDLE / IN_ATTEMPT / AWAITING_RESUME / TEARDOWN` | attempt/resume 状态字段散落 |
| 观察者 | 用 `EventBus` 替代 `env._darwin_post_step` monkey-patch；env 持有 `EventBus` 引用，`subscribe/post` 标准化 | 跨包私有字段耦合 |
| 适配器 | `DarwinEnvWrapper(env, hooks)` 把物理快照/action 标记/物理观测集中处理 | 钩子集中、env 不被 monkey-patch |
| 工厂 | `RunnerFactory.build(task_name, config)` 注入 planner+executor+reflector+mutator | `DynamicEpisodeRunner` 拆分后，组装点明确 |
| 模板方法 | `Runner.run()` 留骨架，把 `observe/plan/execute/reflect/decay` 留作 hook | 主循环 158 行收窄到 ~30 行 |
| 依赖注入 | `DynamicEpisodeRunner.__init__` 收 `(planner, executor, reflector, mutator, rag, agent, registry, experience)` 全部注入，构造内不再 `ManipulationAgent(...)` | 可替换、可单测 |
| 命令分发 | `ipc/dispatch.py` 用 `{msg_type: handler}` dict 替代 `if mtype == "run"/"stop"` | 新增协议字段不修主循环 |

## 五、PR 切分原则（为了"大规模并行 PR"）

为了让团队 / 多 agent 能并行提 PR 而不互相阻塞，遵循以下原则：

1. **一个 PR 只动一个职责**：拆 God class 时按"抽 planner / 抽 executor / 抽 reflector"分 PR，不要在一个 PR 里同时抽 3 个。
2. **先建测试再重构**：阶段 0 的单测 PR 必须先 merge，阶段 1+ 的重构 PR 才能放心改。
3. **保持向后兼容**：删 `darwin/memory/rag.py` 时，先保留 `from darwin.memory import RAGMemory` 重导出，给下游脚本迁移时间；删 `runner.py` 时先把 4 个旧脚本迁完再删。
4. **避免大爆炸合并**：禁止"一次性重构 1000 行"的 PR；每个 PR ≤ 300 行 diff，可独立 review。
5. **PR 标题前缀化**：`[refactor/runner]`、`[test/darwin]`、`[ci]`、`[scripts]`、`[docs]`，方便筛选与并行分配。
6. **每 PR 都跑 CI**：阶段 0 的 CI 先建立，后续 PR 一律 gate 在 CI 绿色上。
7. **分支命名约定**：`refactor/<阶段号>-<子任务>`，例如 `refactor/2a-planner`、`refactor/3d-env-wrapper`，多 agent 并行时不撞名。

## 七、需要决策的开放问题

1. **`darwin` 是要发布到 PyPI 还是只做仓库内包？** 这决定 `pyproject.toml` 是否要补完整 metadata。
2. **`ragbot` 与 `darwin.memory` 的关系最终是"独立 PyPI"还是"`darwin.memory` 是 `ragbot` 的薄壳重导出"？** 前者更解耦，后者更省事。
3. **`robopal` 是否要 fork 出内部版？** 它当前是 fork 自外部仓库（`url = github.com/NoneJou072/robopal`），未来如果要改 robopal 源码适配 darwin 钩子，需要决定长期同步策略。
4. **forged skill 持久化位置**：放 `logs/forged/` 还是单独的 `darwin_forge/` 仓库？前者与代码解耦简单，后者便于跨机共享。
5. **是否引入 `dynaconf` / `pydantic-settings` 这类配置库？** 还是只用 dataclass + YAML？后者依赖最少。

## 八、一页纸总结

当前架构的核心问题可以浓缩成三句话：

1. **三个包互相缠绕**：`darwin` / `robopal` / `ragbot` 没有清晰的依赖方向，`darwin` 还重复实现了 `ragbot` 的 RAG。
2. **两个 God Class**：`SimWorker` 400 行 9 职责、`DynamicEpisodeRunner` 996 行 12 职责，状态用散落字段隐式维护。
3. **缺少工程基线**：没有 CI、没有统一 Config、`scripts/` 混乱、`_darwin_*` 跨包 monkey-patch、`darwin` 包没有打包配置。

重构路线：先建测试与 CI（阶段 0）→ 消除冗余（阶段 1）→ 拆 God class（阶段 2-3）→ 治理边界与打包（阶段 4）→ 整理脚本与文档（阶段 5）。每个 PR ≤ 300 行、单一职责、可并行 review、CI 红绿即可合并。
